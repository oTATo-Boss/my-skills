# 优先调用与持续优化

## 原生发现机制与接入边界

核实日期：2026-10-30。官方 [Build skills](https://learn.chatgpt.com/docs/build-skills) 说明，Codex 先加载 name、description 和路径，再按需读取正文；用户可显式点名，也可由模型按 description 选择。其本地发现覆盖仓库 `.agents/skills`、用户、管理及系统目录，软链接受支持，同名入口不会自动合并。当前会话的实际插件清单及客户端启用状态仍需单独核对。

本机 `codex-cli 0.163.0` 的 `codex app-server generate-json-schema` 生成协议中，`SkillMetadata` 提供 name、description、path、scope、enabled、interface、dependencies 等字段，未提供质量分／排名权重。它支持发现和启停，不构成本管理器的评分路由器。`agents/openai.yaml` 的 `allow_implicit_invocation` 控制是否允许隐式调用，不是数字优先级。`SKILLS_INDEX.md` 和自定义 `SKILL_QUALITY.json` 不会自行被 Codex 解释成原生排名；不添加无效的 `priority` 元数据来假装接管调用。

实际接入使用两层：

1. 正常发现仍依赖准确的 name、description、客户端入口和启用状态。管理器只在安装、更新、审计或同类候选择优时加载；不把 description 扩成“任何任务都先审计”。
2. 需要让某项目的日常选型使用评分时，在其现有 AGENTS.md 中加入下面的轻量指令，指向真实管理器参考和档案位置。Codex 会按 [AGENTS.md 官方机制](https://learn.chatgpt.com/docs/agent-configuration/agents-md) 加载项目指令；这是模型遵循指令的选型流程，不是宿主的不可绕过拦截器。其他客户端沿用各自指令入口。本项目已接入同等规则，不修改全局客户端配置；在其他项目／全局启用需要另行按授权接入。

可按实际路径改写的接入段落（不是拥有索引条目）：

```text
Skill 选型先尊重用户明确指定，再按项目／分类索引找到相关能力；存在同类竞争候选及已维护的 SKILL_QUALITY.json 时，先读取 skill-library-management 的 references/routing-and-refresh.md，核实当前场景、运行条件及版本，再运行其 scripts/quality_registry.py select，以 selected 作为优先入口，不能只读分数后自行心算排序。候选事实可用现有请求文件或 --request - 从标准输入传入，未经核实不照用旧请求。needs_review／无档案时据实际能力作暂定判断并标待评，不阻塞正常任务。只加载相关候选，不触发全库审计。
```

接入验收分三层报告：指令／索引路径可达、脚本对候选输入的选型行为、客户端实际是否读到指令并选中入口。前两项通过不冒充模型选型实验已完成；客户端新会话中用典型任务和易混淆反例验证第三层。v1.4.1 的 CLI 隔离实测记录见 [原生调用验收](../evals/native-invocation.md)，其中区分了读取评分后自行选择与真正调用选择器的证据。当前会话不会因磁盘规则更新就可靠地重新加载全部指令；必要时新开会话验证，不声称已即时全局生效。

## 轻量候选选择

1. **明确指定优先。** 按完整 ID／入口定位，读取用户指定 Skill。若依赖阻塞或任务明确不适配，说明具体限制，不暗中用最高分替代；分数未评或过期本身不否决用户指定。
2. **语义匹配。** Agent 根据当前输入、期望产物、专业约束与项目可见范围选出少数同类候选；将本次竞争归入同一 `scenario` 任务契约。跨场景分数不能混用；职责互补的组件各选所需角色，再组合使用。
3. **运行条件。** 核对必要工具、依赖、平台、账号可用性和入口当前版本／内容修订。准备度不能从高分推断，不为选型自动安装依赖或发起收费业务调用。
4. **分数选择。** 符合任务且条件满足的候选，优先选当前证据充分的最高综合分。同类候选缺分或过期时，不按 0 排到最后；若其可能分数影响选择，补最必要的证据或将结果标为待核验，再由 Agent 在任务可执行的候选中作有依据的暂定选择。
5. **接近时取舍。** 默认 3 分以内为接近，可在请求中通过 `near_points` 明确调整。优先本人原创，再深度二创，再其他；随后比同场景当前版本的真实成功调用次数、专业适配（exact 优于 related）、分数。仍完全相当用稳定 ID 排序保证结果可复现，不把该顺序解释成质量优劣。

`quality_registry.py select` 只执行确定性的过滤与排序，Agent 提供语义结论与当前条件证明。输入见 [候选请求模板](../assets/selection-request.example.json)：候选 `fit` 为 exact／related／none／unknown，`conditions` 为 ready／blocked／unknown，附核对依据、当前版本和 revision。所有同名实体用不同 ID，显式指定也用 ID，避免误选。待评候选也先建未评分档案；没有档案时 Agent 可直接遵循上述流程选用并标记待评，无需为每个日常调用生成文件。

有可用档案的同类候选实际竞争时，核实请求事实后调用选择器，使用其 selected／blocked_explicit／needs_review 结果；不能只按肉眼总分或旧候选文件直接执行。依赖证据注明路径基准（项目根、Skill 根或脚本目录），按实际脚本解析方式核对，不能把项目根的 deps/ 误查到 Skill 根。明确指定可直接按该入口核实执行；无关任务不读档案、不运行选择器。

```bash
python3 scripts/quality_registry.py select /path/to/SKILL_QUALITY.json \
  --request /path/to/task-candidates.json --as-of YYYY-MM-DD
```

只读会话可将相同请求 JSON 传给 `--request -`，不必在项目中生成候选文件；标准输入只提供数据，不拼接进 shell 命令。实际调用先读取返回的 selected.entry，再读取该 Skill 的真实流程并执行，不能把选择器返回当作业务任务已完成。

返回 `explicit`／`selected` 时给出所选入口、分数、Star、来源与证据；`blocked_explicit` 表示指定项不满足运行／匹配条件，不自动替换；`needs_review` 表示分数区间或条件尚不支持确定赢家；`no_match` 表示没有可选项。脚本不执行被选 Skill，也不改 name、入口、索引或配置。版本／revision 不匹配使旧分失效，显式指定在当前任务和运行条件已核实的前提下可继续使用，但输出保留旧分不可用的状态。

输出的 `ranked` 是符合条件且证据完整候选的纯分数顺序；`selected` 才是应用“接近时来源／使用／适配偏好”后的最终优先项，二者可能不同。报告须说明取舍，不能把纯分数列表直接当作最终调用顺序。

真实记录用 `runs` 保存唯一 ID、任务、Skill 版本、时间、成功／失败、证据位置及验证状态。脚本只用已验证、同场景、当前版本的成功次数作接近时的取舍；未知使用历史不造数。可靠性评分应同时参考失败记录与样本偏差，不能凭“多用”遮盖高失败率。

## 生命周期中的持续优化

“自动检查”是 Agent 在已触发的管理流程中执行相应步骤，不是后台守护进程。安装／更新 Skill 的授权覆盖相应记录维护，不自动授权处理其他重复候选；只读审计只输出草稿档案和方案，不落盘修改库。

| 触发 | 最小评估范围与动作 |
|---|---|
| 新增 Skill | 读取包、来源、依赖，沿相关索引找同类能力与跨名称替代关系；核实原始仓库 Star 和归属，建立必要评分（缺证据记未知），比较重复和独特能力，再按既有安装流程维护记录、映射与客户端入口。 |
| 更新 Skill | 比较版本／内容和依赖差异；改流程、脚本或产物则重评效果、可靠性及覆盖，改文档则评维护及调用边界，变更来源则核实归属和 Star。未受影响项可复用原证据，但须注明沿用依据、将 assessed_version 更新为新版本并保留证据原版本；脚本不自行证明“不受影响”。 |
| 已有真实运行结果 | 只提取当前已授权可读记录，去重运行 ID，补入对应场景和版本；失败、依赖变化或输出缺陷及时将受影响指标标 stale 并重评，不扫描全部会话或私人日志。 |
| 周期复核／用户提出优化 | 按 review_after 筛选本次范围内到期项，复用真实产物、仓库数据和维护信息；只刷新相关项。无新证据则继续未知，不能靠日期滚动维持满分。需要后台定时运行时另按用户要求配置自动化，本 Skill 自身不创建定时任务。 |
| 更优新候选 | 同场景、相同条件下有可信且稳定的分数优势，并且实际效果／可靠性不退步、独特能力有保留去向时提出替代建议。默认分差超过 near_points 才称明显优势；仅 Star 或未知分带来的差距不足以自动淘汰。本人开发项优先提出吸收优秀流程／能力的升级方案，并保留第三方来源和许可。 |

评分档案不嵌入拥有索引，也不改变原有数量口径。索引保持「名称 — 一句话用途」和真实入口；最多导航到管理档案，不复制一份动态分数。归档／迁移时同步所评入口、ID 关联、档案状态和依赖引用，保留历史结果；复制到安装位置也不重复计算。执行仍依 [变更与校验](change-checks.md) 的授权、备份和回滚流程。

## 审计报告

全量报告按既有发现范围给出逻辑 Skill 总数、实体数、客户端入口数及不可访问限制；局部报告明确局部数量，不声称全库总数。每项列 ID／入口、任务场景、重复关系、六项分数或未知状态、确定总分／区间、原始 GitHub Star 与查询日期／仓库口径、原创／二创归属、实际调用记录、运行条件、调用优先级及理由、保留能力去向、建议动作和验证状态。执行后再列实际处理结果、源码／安装／客户端检查及具体备份回滚记录。
