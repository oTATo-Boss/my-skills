# 统一质量档案与 100 分制

本规范替代早期版本“不设固定分数”的约定；语义关系仍由 Agent 判断，分数不自动决定删除或合并。每个逻辑 Skill 可按任务场景维护多个档案，不重复登记源码／安装／链接。不同用途可以共用格式，只有相同或高度相关的任务契约、约束和运行环境才参与竞争排名。

## 轻量参考评估与实测评分分开

默认先复用已有档案，针对实际用途阅读入口、关键参考与决定行为的脚本，逐项完成内容审阅，避免为了填表机械启动全部业务。保留上述六项原权重。

- `review_assessment` 保存参考评估：`basis: content_review`、日期、版本、包修订、置信度、输入／输出／验收条件、已读文件、四项 points/reason、优点、具体短板及有边界的历史运行证据。效果分是预期任务效果、可靠分是实现与依赖风险判断；不是已观测成功率。长资源库可按当前用途审阅关键资料，但须说明抽样边界，不能称全包逐字核验。
- 四项质量合计 `/70`；`github_review` 与 `ownership_review` 分别使用下方 Star 和贡献规则，各 `/15`。每项必须有具体依据；不按目录数量、统一默认分或所有者名机械赋值。
- `reference_score` 从同一 JSON 的去重仓库快照取事实，不联网。元信息未知时给参考分上下界，不给确定总分、不把未知填 0，也不归一化。快照超过7天不作当前确定社区分。
- 查询中的 `reference.total` 是**参考评估分**，不覆盖原 `metrics`、runs、严格 `total` 或实测完成状态。包内容变化时通过 `--check-current` 将参考分标为 stale；按变更重评。每次更新保留原评估于 history。
- 原 `score/select` 仍按严格证据规则运行；参考分可供 Agent 在同类任务、依赖满足时解释选型，不能输入严格选择器冒充实测赢家。缺口区间相交时不声称确定优胜。不同业务不可按参考总分全库淘汰。

内容审阅完成数、得到确定参考分数、元信息缺口数、严格实测完成数分别报告。只新增档案或空字段仍然不算审阅完成。已有真实运行只证明所记录场景，不能给未测试分支背书。用户需要实际效果认证时再对相关候选补任务验证，不增加日常全库执行负担。

## 六项评分

| 维度／字段 | 上限 | Agent 评估与证据 |
|---|---:|---|
| 实际任务效果 `effect` | 25 | 对照预先说明的任务和验收标准，检查实际产物、完成度和质量；记录输入、输出位置、失败点与样本范围。未运行不能以文档漂亮代替效果证据。 |
| 执行可靠性 `reliability` | 20 | 真实运行的成功／失败样本、重复稳定性、异常处理、必要依赖及环境。记录样本数与失败原因，单次成功不宣称长期高成功率。 |
| 功能完整度 `capability` | 15 | 对照该任务所需能力，核对核心流程、专业约束、独特分支及验收闭包；独特能力必须有明确位置。 |
| 维护质量 `maintenance` | 10 | 当前兼容性、可读文档、可维护结构、测试及有效修复记录；时间新旧或更新次数不直接等于质量。 |
| GitHub Star `github` | 15 | 原始仓库的真实 `stargazers_count`，附查询时间、API／连接器来源、原始仓库归属和独立／合集判断；按下节计算。 |
| 本人开发 `ownership` | 15 | 原创 15；深度二创为 `15 × contribution`；外部收集 0；无法确认则未知。核对 SOURCE.md、用户已确认的开发记录和 Git 历史／实际差异，不能只看 Git 作者、当前托管仓库或文件存在。 |

前四项由 Agent 在对应上限内赋分并说明具体扣分依据：0 表示有证据证明该项未满足；中间分表示已验证的部分覆盖且缺陷明确；满分要求本次任务验收所列标准全部有支持证据。先固定验收任务再评价，不按名称、描述长度或 Skill 数量打分。脚本只验证范围、证据字段和算术，不能认证 Agent 对产物质量的判断。

深度二创的 `contribution` 在 0 与 1 之间：按实际重写／新增的核心工作流、脚本、专业约束和独特能力说明贡献份额。例如核心流程约半数由本人重新实现可评 0.5，主要流程已重建且保留部分上游可评 0.8；必须逐项举证，不用代码行数比例机械计算。浅层改名、翻译或重新安装不能冒充深度二创，按收集记录 0。只有原创取得来源项满分及最高来源偏好；已确认的本地归属不因缺失上游作者／许可而降为未知，详见 [来源记录](source-records.md)。

本人开发是长期维护偏好，不等于已高频使用。仅有可核验运行记录时，才记录实际使用次数；区分成功和失败，并保留场景、版本、时间及运行 ID，不能把索引引用、文件访问、安装次数或推测的“常用”当调用记录。

## Star 的核实与单调对数分档

先用来源记录确认原始仓库和 Skill 在其中的路径；区分上游、二创维护仓库、fork、搬运镜像及参考工具。不能将热门依赖、素材仓库或当前合集的 Star 冒充该 Skill 的独立认可。使用连接器／官方 API 获取完整整数，网页的 `1.2k` 只作线索。接口失败、限流、私有不可读及无可靠来源均为未知，不是 0 Star。

令真实 Star 数为 `s ≥ 0`，`L = log10(1 + s)`，基础分 `B = 15 × L / (L + 1)`。用十倍档组织解释并连续计算，不在档内强行同分：

| Star | 0 | 9 | 99 | 999 | 9,999 | 99,999 |
|---|---:|---:|---:|---:|---:|---:|
| 基础分 B | 0 | 7.5 | 10 | 11.25 | 12 | 12.5 |

独立 Skill 仓库 `dedicated` 使用 B；包含多个独立技能的大型合集 `collection` 使用 `0.5 × B`，表示合集层面的间接认可，原始 Star 数保持原值展示。0.5 是本版明确的归属折算政策，不是测得的社区份额；不能在候选间随意调整。原始仓库或归属类型未确认时不计确定分。相同归属口径下，Star 增加使未舍入分数严格增加，分数渐近 15，避免大仓库全部饱和同分；显示取四位小数可能相同。不同归属口径不可只按原始 Star 排序。

明确没有 GitHub 来源（例如仅本地原创、非 GitHub 托管）时可记 `not_applicable`，此项按已知 0 计且权重仍为 15；不能把该权重转给其他维度。已知有 GitHub 但读不到时必须记 `unverified`。

只读获取示例：`python3 scripts/quality_registry.py github owner/repo`。脚本仅访问 GitHub 官方仓库接口，输出真实整数、请求与规范仓库名、查询时间、fork／归档状态；不访问密钥、不写缓存、不判断 Skill 归属。发现仓库重命名或 fork 时由 Agent 重新核实来源。已有连接器能提供足够数据时优先使用连接器，按相同字段整理；CLI 是独立可用的公共仓库后备路径。实测接口依据 GitHub [仓库 API](https://docs.github.com/en/rest/repos/repos#get-a-repository)，脚本 API 版本固定 `2022-11-28`。

脚本默认使用 Python 标准库 HTTPS；请求失败时若已安装 `gh`，通过其官方 API 命令后备查询，不读取或输出认证配置，不关闭 TLS 校验。两条路径均失败则非零退出并标未验证；不自动安装 gh 或更改本机证书。私有仓库优先使用已授权的连接器或现有 gh 身份。

## 档案、证据与未知项

示例格式见 [质量档案模板](../assets/quality-registry.example.json)，它不代表真实评估。共享库唯一数据源固定为 `~/.agents/skill-library-management/SKILL_QUALITY.json`，同目录 `SKILL_QUALITY.md` 是唯一派生展示表；不另存项目／日期版本的当前评分表。保留 `schema_version: 1`、`profiles`，仓库快照和历史评估置于同一 JSON。相同 `id + scenario` 只有一份当前档案，客户端别名不重复评分。具体批量查询、历史复用、增量更新、原位生成与查询命令见 [统一档案流程](shared-quality-store.md)。

档案包括逻辑 ID、name、真实入口、Skill 版本、所评实体内容修订标识 `revision`、任务契约 `scenario` 和评估日期 `evaluated_at`。`revision` 用实际 Git 提交加工作区差异摘要，或目标包内容哈希标识；未提交修改不能只写 HEAD。源码／安装分歧时分别记录所评实体，不能把源码的测试分直接赋给有差异的安装副本。

四个定性维度保存 `points`；Star 和本人开发分由脚本从结构化字段计算。六项都保存 `status`、`assessed_version`、`review_after` 与 `evidence`。每条证据有 `source`（文件及定位／运行报告／API URL）、`version`（对应证据版本或提交）、`observed_at` 和 `verification`（`tested` 实测、`inspected` 查阅、`reported` 仅声明）。运行、来源判断、Star 查询分别建证据，不能用来源已确认代替实际效果已验证。已验证记录至少有实测或查阅证据；效果和可靠性必须有实测证据。

- `verified`：此版本／任务有足够证据，计入确定分。
- `partial`：仅部分验证，可保留指示分但不计入确定总分；写明缺口。
- `unverified`：未验证，`points: null`，不填假分。
- `stale`：版本或环境变化、超过复核日期，须重评。脚本发现 `assessed_version` 不符或超过 `review_after` 时自动视为 stale。
- `not_applicable`：只用于已确认不存在 GitHub 来源的情形，已知 0，仍保留权重和证据。

`review_after` 由维护者按指标变化速度与风险指定：Star、外部依赖通常比已确认作者归属更快过期，不硬编码所有指标同一时限。任一项未知／部分／过期时，总分 `total` 为 null，另给确定分下界 `known_points`、可能上界 `possible_max` 和已验证权重 `verified_weight`；不把剩余权重归一化，也不把未知称作实际 0。所有记录包括未验证项都带本次评估日期和目标版本，未知项允许空证据并明确原因。

```bash
python3 scripts/quality_registry.py score ~/.agents/skill-library-management/SKILL_QUALITY.json --as-of YYYY-MM-DD
```

脚本不读取其他 Skill、不自动运行评测、不写回分数；外部事实及语义评分的真实性由相应证据和 Agent 复核，结构通过不能宣称全部事实已认证。评分、调用与更新衔接见 [选型与持续优化](routing-and-refresh.md)。

待评是未完成状态，不是本次评分任务的完成条件。Agent 应先复用当前有效证据，完成可在授权内进行的静态评估与安全验证；具体阻塞、未完成指标和下一步必须列明。单项六维满足后才计入已完成数，不能把模板生成、Star 查询成功或仅来源得分当作完整质量评估。
